## 一、工程目标

V1 工程目标只有四个关键词：

> **轻量、稳定、自包含、可交付。**

比赛版不是《中国诗词宇宙》正式平台的技术缩写版，不搬运 MySQL、Neo4j、向量数据库、RAG 等后台体系。

核心闭环必须在不依赖独立后端服务的情况下运行：

```text
打开
→ 本地内容加载
→ 本地测试计算
→ 展示人生结果
→ 浏览苏轼人生站点
→ 今日东坡
→ 本地生成分享卡
→ 调用平台允许的保存/发布能力
```

## 二、最高工程约束：官方 Skill 优先

小红书官方要求：

```text
从
https://fe-static.xhscdn.com/mini-tool/20260831163932/minitool-zip-builder-1.6.0.skill
下载 Skill

Cursor / Claude Code → .claude/
Codex               → .codex/
其他                 → .skill/

读取 SKILL.md
→ 对当前工作区产物校验
→ 修复
→ 再校验
→ 打包
→ 输出校验摘要和产物路径
```

因此本项目技术约束优先级固定为：

```text
1. 小红书官方当前版本 SKILL.md
2. 本文档 05
3. 总体设计 01
4. 其他产品/视觉建议
```

如果官方 Skill 与本文档冲突，**以官方 Skill 为准，并同步更新本文档**。

工程开发不得在没有阅读 `SKILL.md` 的情况下自行猜测打包结构、入口文件、资源限制或平台 API。

## 三、首次开发前置动作

任何 AI Coding 工具第一次开始实现代码前，必须先执行：

```text
1. 拉取仓库最新 main
2. 下载官方 minitool-zip-builder-1.6.0.skill
3. 放入当前 Coding 工具要求目录
4. 阅读 SKILL.md 全文
5. 输出“官方硬约束摘要”
6. 检查现有仓库是否冲突
7. 再创建工程骨架
```

禁止先凭经验搭建 React/Vite/Next.js 等工程，再反向适配官方规则。

框架是否使用、构建工具如何选择、入口文件如何组织，都应在阅读官方 Skill 后决定。

## 五、领域模块边界

### 5.1 Quiz

负责：

- 题目读取；
- 答案记录；
- 分值累计；
- 平分规则；
- 结果映射。

不得负责：

- 直接拼 HTML；
- 直接写分享图；
- 修改史实数据。

### 5.2 Universe

负责：

- 九站排序；
- 当前站点定位；
- 上一站/下一站；
- 站点数据关联。

### 5.3 Daily Dongpo

负责：

- 本地日期转换；
- 稳定选取今日内容；
- 今日内容展示模型。

### 5.4 Share Card

负责：

- 卡片数据模型；
- 画布布局；
- 字体与换行；
- 图片生成；
- 将结果交给平台保存/发布适配层。

### 5.5 Platform Adapter

所有平台专有能力集中封装：

```text
platform/
├── saveImage
├── publish/share
├── environment
└── capabilityCheck
```

具体 API 名称必须以官方 Skill / 官方文档为准，业务组件不得散落调用平台全局对象。

## 六、内容数据层

### 6.1 运行时只读

V1 的核心历史内容在构建时完成审核，运行时只读。

禁止在页面加载时让 AI 临时生成：

- 苏轼生平；
- 作品原文；
- 诗句；
- 创作背景；
- 历史时间。

### 6.2 数据加载

优先采用本地静态导入或官方容器允许的本地资源方式。

正常使用不应依赖：

- 独立 HTTP API；
- 数据库；
- CDN 上的关键 JSON；
- 在线字体；
- 在线随机图片。

### 6.3 生产数据过滤

构建正式发布包前：

```text
只允许 review_status ∈ {approved, published}
```

发现 `draft`、悬空关联、缺失 source 的原始引文，构建应失败。

## 七、测试算法工程要求

V1 算法必须：

- 确定性；
- 可解释；
- 可测试；
- 不依赖 AI；
- 不采集敏感个人信息。

核心函数应接近纯函数：

```text
calculateQuizResult(answers, quizConfig) -> resultId
```

必须覆盖：

- 正常路径；
- 全部选 A；
- 全部选 B；
- 平分；
- 缺失答案；
- 非法 option ID；
- 配置中引用不存在 mood/station。

---

## 八、本地状态

V1 只保存真正有用的轻量状态，例如：

```text
lastResultId
lastQuizAnswers（可选）
visitedStationIds（可选）
lastDailyDate（可选）
```

原则：

- 不保存不必要的用户画像；
- 不采集医疗/心理敏感信息；
- 用户重新测试后允许覆盖结果；
- 存储不可用时核心流程仍可完成。

具体本地存储能力以官方容器支持为准。

## 九、分享卡生成架构

### 9.1 原则

分享卡必须**程序化稳定生成**，而不是对页面截图。

推荐流程：

```text
Result / Daily 数据
→ ShareCardViewModel
→ Canvas / 官方允许的绘图能力
→ 本地图片产物
→ 预览
→ 保存或发布
```

### 9.2 ShareCardViewModel

```ts
interface ShareCardViewModel {
  type: 'station' | 'daily' | 'favorite_station'
  brand: string
  title: string
  subtitle?: string
  keywords: string[]
  quote: string
  attribution: string
  interpretation?: string
  action?: string
  backgroundAsset?: string
  footer: string
}
```

### 9.3 卡片渲染必须处理

- 超长诗句自动换行；
- 不同屏幕密度；
- 字体加载失败回退；
- 背景图失败；
- 中文标点行首行尾；
- 小红书信息流缩略图可读性；
- 生成失败后的重试与提示。

## 十一、样式工程

建立统一 Design Tokens：

```text
colors
typography
spacing
radius
shadow
motion
z-index
safe-area
```

禁止：

- 页面内大量内联 magic number；
- 同一种颜色出现多个近似硬编码；
- 每个页面自行定义按钮样式；
- 结果卡与页面各自维护完全不同的品牌色。

---

## 十二、性能原则

### 12.1 首屏

首页不应等待全部站点大图加载完成才可操作。

优先：

```text
核心 HTML/UI
→ 首屏必要背景
→ 测试数据
→ 次级站点素材
```

具体加载机制以官方容器能力为准。

### 12.2 动效

- CSS/Canvas 动效低频；
- 不创建大量永久粒子对象；
- 页面不可见时尽量停止无意义动画；
- 低端设备优先稳定。

### 12.3 图片

- 使用适合容器的现代压缩格式（若官方允许）；
- 不把超大原图直接打包；
- 分享卡背景与页面背景按用途分别导出；
- 视觉上看不出差别的情况下优先更小资源。

## 十三、错误处理

统一错误对象：

```text
code
module
message
context
recoverable
```

建议错误码：

```text
CONTENT_INVALID
QUIZ_CONFIG_INVALID
RESULT_NOT_FOUND
ASSET_LOAD_FAILED
CARD_RENDER_FAILED
PLATFORM_CAPABILITY_UNAVAILABLE
STORAGE_FAILED
```

用户提示文艺化可以存在，但日志必须保留真实技术信息。

## 十四、测试体系

### 14.1 单元测试

至少覆盖：

- quiz 评分；
- tie break；
- daily 日期选择；
- ID 关联；
- 文案选择；
- 分享卡文本换行算法；
- 数据过滤。

### 14.2 集成测试

至少覆盖：

```text
首页 → 测试 → 结果
结果 → 分享卡
首页 → 今日东坡 → 今日卡
首页 → 宇宙 → 站点 → 下一站
```

### 14.3 内容测试

自动检查：

- 重复 ID；
- 无来源原始引文；
- 悬空引用；
- 结果缺卡片模板；
- 站点没有可展示作品；
- 非 approved 数据进入生产包。

### 14.4 真机/官方环境测试

必须在小红书官方支持的真实预览/运行环境完成最终验收，不能只以桌面浏览器“看起来正常”为通过。

---

## 十五、日志与调试

开发模式允许详细日志；生产模式只保留必要错误。

禁止生产环境输出：

- 用户完整答题内容的无必要日志；
- 大段内容数据；
- 平台授权信息；
- 敏感环境信息。

---

## 十六、依赖管理

V1 原则：**能不用依赖就不用，能用小依赖就不用大框架。**

新增第三方依赖前必须判断：

1. 官方 Skill 是否允许；
2. 是否明显增加包体；
3. 是否只是为了一个很小功能；
4. 是否能使用原生能力替代；
5. 是否有明确许可证。

不得为了“工程现代化”引入大量与比赛需求无关的依赖。

---

## 十七、安全与隐私

- 不做账号密码；
- 不要求输入真实姓名；
- 不询问医疗诊断；
- 不将测试答案定义为心理健康数据；
- 不接入与核心功能无关的第三方追踪 SDK；
- 分享前让用户看到最终卡片内容；
- 平台授权能力严格按官方流程使用。

## 二十、官方 Skill 校验流水线

项目进入交付阶段必须执行：

```text
A. 内容校验
   scripts/validate-content

B. 资源校验
   scripts/validate-assets

C. 本地测试
   unit + integration

D. 官方 Skill 校验
   严格读取 SKILL.md 执行

E. 修复全部阻塞项

F. 重新执行 A—D

G. 官方 Skill 打包

H. 输出：
   - 校验摘要
   - 版本/提交号
   - 产物路径
   - 已知非阻塞问题（如有）
```

禁止只“执行打包命令成功”就宣布完成。

## 二十三、技术最高原则

> **比赛版首先是一个能完整跑通、能稳定分享、能通过官方校验的小工具，其次才是一个技术展示项目。**

如果“更炫的技术”与：

- 稳定；
- 包体；
- 可校验；
- 内容准确；
- 分享闭环；

发生冲突，一律优先后者。
