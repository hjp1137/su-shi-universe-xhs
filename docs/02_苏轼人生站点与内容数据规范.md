> 项目：`su-shi-universe-xhs`

---

## 一、文档目的

本文档定义《苏轼宇宙》V1 的**内容数据底座、人生站点模型、状态匹配模型、诗词关联规则和内容审核状态**。

本规范不是一份“苏轼百科”，而是一份供产品、内容、设计和开发共同使用的数据契约。

V1 所有核心页面必须建立在结构化数据之上，禁止把关键史实、诗词原文、测试结果文案长期硬编码在组件中。

核心数据链固定为：

```text
用户状态
→ 状态维度
→ 苏轼人生站点
→ 经审核的历史事件
→ 经审核的作品 / 诗句
→ 产品解读
→ 今日小行动
→ 分享卡
```

---

## 二、最高内容原则

1. **史实与产品解读严格分层。**
2. **诗词原文与现代改写严格分层。**
3. **不为了“治愈感”虚构苏轼经历。**
4. **不伪造苏轼名言。**
5. **存在学术争议的时间、地点、创作背景必须保留争议状态。**
6. **人生站点是产品叙事节点，不等于严格历史分期。**
7. **用户状态是生活状态匹配，不是心理诊断。**
8. **V1 宁可少而准确，不以数量换完整感。**

---

## 三、V1 数据域

建议本地数据目录：

```text
data/
├── stations.json          # 9 个核心人生站点
├── events.json            # 重要历史事件
├── works.json             # 20—30 首/篇核心作品
├── quotes.json            # 30—50 条可展示原文
├── moods.json             # 8 类生活状态
├── quiz.json              # 测试题与评分规则
├── daily-dongpo.json      # 今日东坡内容
├── actions.json           # 今日小行动
├── share-copy.json        # 分享卡文案模板
└── sources.json           # 来源与版本元数据
```

如工程实现更适合 TypeScript，可将静态数据转换为 `.ts`，但字段语义不得改变。

## 四、统一 ID 规范

所有实体必须有稳定 ID，不以中文标题作为主键。

建议：

```text
station_meishan
station_jingshi
event_wutai_case
work_dingfengbo_moting
quote_dingfengbo_moting_01
mood_anxious
quiz_q01
source_sswj_001
```

规则：

- 全小写英文；
- 单词使用下划线；
- ID 一旦进入正式版本不随展示文案改变；
- 同一作品不同版本通过 `version_id` 区分，不新造作品 ID；
- 分享卡、收藏或本地历史记录只存稳定 ID。

### 5.3 站点页面内容层级

每个站点固定采用：

```text
A. 你到了哪里
B. 苏轼当时发生了什么
C. 他在这里写下什么
D. 他怎样把日子重新过起来
E. 这件事今天可以怎样理解
F. 今天做一件小事
```

A—D 必须受史实与作品证据约束；E—F 属于现代产品层。

## 七、作品模型

### 7.1 V1 作品范围

首版控制在 **20—30 首/篇**，优先选择同时满足以下条件的作品：

1. 与九个人生站点有较强关系；
2. 普通用户有一定认知基础；
3. 能体现苏轼不同的人生面向；
4. 适合移动端截取短句展示；
5. 能支持正向但不过度鸡汤化的当代连接。

总体方案中已列出的优先候选包括：

- 《江城子·密州出猎》
- 《水调歌头·明月几时有》
- 《江城子·乙卯正月二十日夜记梦》
- 《定风波·莫听穿林打叶声》
- 《念奴娇·赤壁怀古》
- 《赤壁赋》
- 《临江仙·夜归临皋》
- 《饮湖上初晴后雨》
- 《惠州一绝 / 食荔枝》
- 《六月二十日夜渡海》

这些是**候选清单**，正式进入 `works.json` 前仍需逐篇校核版本、标题、创作时间、关联站点与出处。

### 7.2 作品数据结构

## 八、诗句与引文模型

### 8.1 引文类型必须明确

`quote_type` 建议：

```text
original_poem       # 诗词原文
original_prose      # 散文/书信等原文
historical_record   # 史料直接记载
modern_paraphrase   # 现代释义
product_copy        # 产品原创文案
```

只有前三类可使用类似“苏轼写道/说过”的表达。

`modern_paraphrase` 和 `product_copy` 必须在数据层标注，UI 不得使用引号制造“古人原话”错觉。

### 8.2 数据结构

```json
{
  "id": "quote_xxx",
  "text": "原文或现代文案",
  "quote_type": "original_poem",
  "work_id": "work_xxx",
  "source_ids": [],
  "context_note": "上下文说明",
  "review_status": "draft"
}
```

## 九、用户生活状态模型

V1 固定 8 类，不使用医学化术语：

| mood_id | 用户可见名称 | 核心维度 | 推荐主题 |
|---|---|---|---|
| `mood_anxious` | 最近总有点慌 | 节奏失控 | 风雨 / 徐行 |
| `mood_work_stuck` | 工作不太顺 | 受挫 / 重建 | 黄州 |
| `mood_misunderstood` | 很在意别人怎么看 | 外部评价 | 乌台之后 |
| `mood_overthinking` | 想得太多，停不下来 | 反复预演 | 徐行 |
| `mood_tired` | 最近真的有点累 | 精力下降 | 慢一点 |
| `mood_lost` | 不知道下一步往哪走 | 路径不确定 | 贬谪之路 |
| `mood_lonely` | 有点孤单 | 独处 / 思念 | 月夜 / 赤壁 |
| `mood_ordinary` | 日子平平，但想过好 | 日常意义 | 东坡烟火 |

用户界面避免“你是焦虑型人格”等标签式表述。

## 十、测试题与匹配算法

### 10.1 算法目标

V1 使用**可解释、确定性的本地评分模型**，不依赖实时 AI。

每道题的答案只给若干 `mood_id` 或 `station_id` 加权。

示例：

```json
{
  "id": "quiz_q01",
  "question": "最近最让你费心的是什么？",
  "options": [
    {
      "id": "a",
      "text": "事情很多，脑子停不下来",
      "scores": {
        "mood_anxious": 2,
        "mood_overthinking": 3
      }
    },
    {
      "id": "b",
      "text": "努力了，但事情还是不顺",
      "scores": {
        "mood_work_stuck": 3,
        "mood_lost": 1
      }
    }
  ]
}
```

### 10.2 推荐流程

```text
5—8 道题
→ 汇总 mood 分数
→ 选出最高 mood
→ mood 映射候选 station
→ 根据次高维度进行站点细分
→ 结果稳定化
→ 输出 result_id
```

### 10.3 稳定化规则

- 同一组答案必须得到同一结果；
- 平分时使用明确的 `tie_break_priority`，禁止随机；
- 不根据设备、用户身份、账号信息暗中改变结果；
- 每个站点都应有可达到路径，但分布不强求人为均匀；
- 测试结果文案必须有明显区分。

### 10.4 结果结构

```json
{
  "result_id": "result_huangzhou_rebuild",
  "station_id": "station_huangzhou",
  "primary_mood_id": "mood_work_stuck",
  "title": "你正走到苏轼的黄州时刻",
  "keywords": ["慢一点", "重新生活", "继续往前"],
  "quote_id": "quote_xxx",
  "dongpo_view": "产品解读",
  "action_id": "action_xxx",
  "share_template_id": "share_station_v1"
}
```

## 十一、“东坡式理解”规范

`dongpo_view` 是本产品最重要的原创层之一。

它不是古文翻译，也不是替苏轼“说话”，而是：

> **基于经审核的人生经历与作品，为当代用户做一次克制的生活化解释。**

推荐写法：

```text
事实：当时发生了什么
↓
观察：作品呈现了什么姿态
↓
连接：今天的人可以从中看到什么
```

禁用写法：

- “苏轼告诉你：你一定会成功。”
- “苏轼早就看透了焦虑症。”
- “这首词可以治愈你的抑郁。”
- “你现在和苏轼完全一样。”

## 十二、今日小行动模型

今日小行动必须满足：

- 低门槛；
- 无医疗暗示；
- 不涉及危险行为；
- 不要求消费；
- 通常 1—20 分钟可完成；
- 与对应诗句或人生主题有自然联系。

类型建议：

```text
walk       散步
pause      暂停一件事
write      写一句话
food       好好吃一顿/做一道简单食物
look       看月亮/看云/看树
contact    联系朋友或家人
organize   整理小空间
read       读一小段诗文
```

数据结构：

```json
{
  "id": "action_walk_10min",
  "type": "walk",
  "text": "把一件今天解决不了的事先放下，出去走十分钟。",
  "mood_ids": ["mood_anxious"],
  "station_ids": ["station_huangzhou"],
  "review_status": "approved"
}
```


前台不必把完整书目全部展示，但后台数据必须可追溯。

## 十五、审核状态机

建议统一：

```text
draft
→ fact_checked
→ text_checked
→ product_reviewed
→ approved
→ published
```

含义：

- `draft`：初稿；
- `fact_checked`：史实与出处已核；
- `text_checked`：原文、标点、版本已核；
- `product_reviewed`：现代解读、行动建议、情绪边界已审；
- `approved`：可进入正式构建；
- `published`：已进入发布包。

任何 `draft` 数据不得进入正式比赛包。

---

## 十六、数据质量门禁

构建前至少执行以下检查：

```text
[ ] 所有 station_id 唯一
[ ] 所有关系 ID 均能解析到真实实体
[ ] 所有 original_* 引文均有 source_id
[ ] 所有 works 均有 review_status
[ ] 所有结果均有 station、quote、action
[ ] 所有产品解读均未伪装成苏轼原话
[ ] 所有测试结果都可通过至少一种答题路径到达
[ ] 所有今日东坡条目可正常渲染
[ ] 所有分享卡引用的诗句长度满足版面限制
[ ] 正式构建只包含 approved/published 内容
```

建议后续增加自动校验脚本，例如：

```text
scripts/validate-content.*
```

内容校验通过后，再进入小红书官方 Skill 的工程校验与打包。

## 十七、V1 内容生产顺序

```text
1. 建立 sources
2. 核定九个人生站点
3. 核定核心事件
4. 核定 20—30 首/篇作品
5. 抽取 30—50 条可用引文
6. 建立 8 类用户生活状态
7. 编写 5—8 道测试题
8. 建立结果映射
9. 编写东坡式理解
10. 编写今日小行动
11. 编写 30 条今日东坡
12. 全量审核
13. 导出正式静态数据包
```

## 十八、V1 验收标准

本规范验收通过的最低标准：

- 九大站点结构完整；
- 20—30 首/篇作品均可追溯；
- 30—50 条引文无伪造；
- 8 类生活状态与站点映射可解释；
- 5—8 道测试题可稳定输出结果；
- 30 条今日东坡内容不含医学化承诺；
- 所有现代解读明确属于产品原创层；
- 正式构建数据全部达到 `approved` 或 `published`。

## 十九、与其他文档的关系

- `01` 决定产品为什么做、做什么；
- `02` 决定内容数据长什么样、如何保证可靠；
- `03` 决定这些数据如何被用户看见和操作；
- `04` 决定最终视觉如何统一；
- `05` 决定工程如何实现、校验和打包；
- `06` 决定史实、引文、现代解读如何审核。

后续任务书不得绕过本规范自行发明另一套数据结构。
